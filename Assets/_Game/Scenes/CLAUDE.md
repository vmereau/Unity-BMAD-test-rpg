## Core.unity Manager GameObjects

Manager GameObjects in `Core.unity`:
`WorldStateManager`, `GameEventBus`, `SaveSystem`, `SceneLoader`, `DayNightController`, `AudioManager`

| GO | Status |
|----|--------|
| `WorldStateManager` | Scripted — `Game.Core.State.WorldStateManager` |
| `SceneLoader` | Scripted — `Game.Core.SceneLoader` |
| `SaveSystem` | Scripted — `Game.Core.SaveSystem` (refs wired to the Player instance's components and `UICanvas/ConfirmDialog`; see `Scripts/Core/CLAUDE.md` → Save) |
| `GameClock` | Scripted — `Game.Core.GameClock` (world time; `TimeConfig`, `OnHourChanged`, `OnTimeSkipped`). Referenced by `SaveSystem` and the Player instance's `SleepSystem` / `StatusEffectHost` (scene overrides — `Player.prefab` itself has no clock, so beds refuse with a warning in scenes without one, e.g. `TestScene`) |
| `DayNightController` | Scripted — `Game.Core.DayNightController` (`GameClock`, `DayNightConfig`, children `Sun` / `Moon` directional lights). **Region scenes must not contain a directional light** — the sun lives here (StartingTown's was removed). `TestScene` keeps its own (it runs without Core) |
| `AudioManager` | Scripted — `MusicPlayer` + `AudioSource` (Output = `MainMixer/Music`), `SfxPlayer` (pooled one-shots), `AudioMixerVolumes`; see `Scripts/Audio/CLAUDE.md` |
| `GameEventBus` | Empty stub |

**Active scene / `RenderSettings`:** no code calls `SetActiveScene`, so in a build Core stays active and its Lighting
settings (skybox: built-in Default-Skybox) apply; in the editor the active scene is whichever you made active (often
StartingTown, skybox `SkyboxLite`). Lighting set in a region's Lighting window is therefore editor-only — tune the
look through `DayNightConfig` / Core instead.

`Core.unity` also contains a `Player.prefab` instance — the `PlayerStats` / `PlayerSkills` references in
the scene YAML are that instance's components, not separate scene components.

Enemies live outside the basin: spiders in and at the mouth of the tutorial cave near (85, −45), bandit patrol around (−110, 30). They aren't tool-owned: a Sites run leaves them alone, and moving a site doesn't move them.

**Valley terrain:** 1000 m square (1025 heightmap, about 1 m per sample), origin (−500, −500), with the object at y = −30 and heights +30 so ground can sit below y = 0. The sculpt, paint and forest come from `Tools/World/Build Area 1 Terrain` (`Editor/World/Area1TerrainBuilder`). Sites, river, lake, ford and roads are read from `docs/World/Areas/area-001/layout.json`; ridges, pad heights and the camp footprint are constants in the tool, so moving the ruins or quarry far means moving their ridge too. Every run rewrites `StartingTownTerrain.asset` but keeps hand edits stored in `docs/World/Areas/area-001/terrain-sculpt.bin`: after sculpting, run `Tools/World/Capture Area 1 Terrain Sculpt`. The tool refuses to run while the terrain has uncaptured height edits. That check and the capture cover heights only: hand-painted textures and hand-placed trees are overwritten without warning, so those changes go into `layout.json` or the tool. The camp's ground, paint and holes come from `Art/Terrain/StartingTownTerrain_Source.asset` (the original 500 m terrain): don't delete it, and make lasting camp ground edits there. A rebuild scatters the forest from the current heights, so the first run after a sculpt changes trees on the sculpted ground, and a sculpt's whole-centimetre rounding can move heights by one heightmap step (1.83 cm). Water is one `Water_Volume` covering the valley, top at y = −2. Any non-water ground must stay above that, and `NotWalkable_West` / `NotWalkable_East` leave x 31..39 open for the ford. `Area1_Blockout` holds the pass blocker and the waterfall placeholder. Rebake the NavMesh after a re-run. Bake with `NavMeshAssetManager.StartBakingSurfaces`, on `Terrain_StartingArea` only: `NavMeshSurface.BuildNavMesh()` keeps the data in memory, so a scene save drops the reference and the next bake writes a second asset named `... 1.asset`.

**Hand edits:** `Tools/World/Area 1 Hand Edits` (`Editor/World/Area1HandEditsWindow`) keeps edits made inside tool-owned roots. Scan builds both tools into a temporary clone of `Area1_Blockout` and lists what differs from the live scene; Save writes the ticked rows to `docs/World/Areas/area-001/hand-edits.json` and replaces the whole file. Sites and Camp Edge reapply it at the end of each run, with `CampEdge/*` going to Camp Edge and the rest to Sites. It lives beside `layout.json`, not in it, because the planner exports a fixed field list and would drop it. Saved objects are pinned: they keep their stored local transform and stop following the ground themselves, though a saved child still moves with its parent, so a later sculpt can leave them floating. Rerun the tools after a sculpt or layout change, before you hand-edit, because a scan treats any stale object as moved. New height-only rows (position y and scale y, as a panel's height comes from the ground) start unticked for that reason, so tick the ones you moved yourself. Only transforms and existence are compared: materials, components and a disabled object aren't kept. A renamed or reparented object reads as removed plus added, so saving deletes the built original. An object added inside a tool root is listed as lost and can't be saved, so move it out of the root. Saved edits with no difference in the scene stay listed and ticked: untick them to drop them. Each moved entry also stores where the tool built it, because generated names like `Panel_140` count across lines and shift with the layout: a run warns when that changes. A removed entry has no such check. An edit doesn't reach what was built from it, so pinning `GangHouse/GangDeck` leaves `GangDock` at its built height. A part of a prefab instance can't be destroyed, so a removal switches it off. A scan can mark the scene modified, because it builds a clone there. A broken file stops a run before anything is destroyed, and a path that no longer resolves only logs a warning. Keep `GameObject.Find` out of the builders: `Run` takes its root, and anything a builder writes outside that root would be changed by every scan.

**Camp edge:** `Tools/World/Build Area 1 Camp Edge` (`Editor/World/Area1BlockoutBuilder`) reads the `outer-fence*`, `hill-palisade`, `inner-fence-*`, `dock-fence-*`, `compound-fence-*`, `shore-rail` and `ramp-rail` features of `layout.json` and replaces only `Area1_Blockout/CampEdge`; re-run it after any terrain re-run, because panels follow the ground, then rebake. The hill closes it on the south (see **Fort hill**). West of (−31.5, −43.3) `outer-fence` runs along the hilltop, then turns east along the hill's north foot into the wood opening, because anywhere at the bank's foot a running jump from the hill clears the panels. Inside, that leaves a bank about 7 m high in front of the wall, and an empty shelf on the hill behind it. Test this line with a running start from 5 m out; the numbers on `Panel_NNN` count across lines, so adding length to an early line shifts every later name, and saved `hand-edits.json` paths must move with them. East of the north palisade's end at (30, 51.9) it is open round to the inner fence's east end: the wilderness trail and the shore both leave that way (see **Lakeside**). Its blocker uses a collider on `Ignore Raycast`, which the player still hits and sight rays and the camera skip. It owns `CleftBlocker`: `FactRemovedObject` hides its `Seal` child while `WorldFact_QuarryPassageOpened` is true. The bake ignores the blocker (`NavMeshModifier`) and a carving `NavMeshObstacle` closes the cleft at runtime, so removing it needs no rebake. That obstacle stays disabled in the scene, because a bake cuts an enabled carving obstacle into the NavMesh even under an ignore modifier; `FactRemovedObject` enables it in `Awake`. Edit-mode paths therefore go through the cleft: test sealing in play mode. Ground slope, not path grade, decides what the player can climb, so check reachability against surface slope.

## MCP Tool Quirk — Scene Loading

**`manage_scene(action="load")`** only resolves scene names at `Assets/{name}.unity`. It **cannot** load scenes in sub-folders (e.g. `Assets/_Game/Scenes/Core.unity`). Edit `.unity` files directly for sub-folder scenes, then call `refresh_unity`.
